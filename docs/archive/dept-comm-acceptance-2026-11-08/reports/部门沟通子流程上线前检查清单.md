# 部门专属沟通子流程 — 上线前检查清单（测试 / 实施用）

> 适用范围：`camunda-comm-demo` 部门沟通功能（通用子流程 + 法务部合同审查 + 财务部预算审核）
> 依据：三份过程验收报告 + 跨链路汇总验收单（40 步 / 0 失败，H2 + 演示账号环境）
> 使用方式：逐项打勾。**P0 全部为 ✅ 才允许上线；P1 可带条件上线但须登记责任人。**

---

## 0. 两条 P0 高风险先说清

这两条不是"代码可能有问题"，而是"代码没问题也会在真实组织里直接炸"的两处外部依赖。验收报告里 40 步全过，前提是演示数据恰好把这些都配齐了。

### R1 岗位组 / 文书组无人 → 子流程停摆 + 主待办永久锁定

**机理**：三条流程里除「通用流程的分发」由文书在界面上动态选人，其余节点全部由 BPMN 写死组承接（`dept_legal_clerk`、`legal_compliance`、`legal_business`、`legal_manager`、`finance_budget`、`finance_treasury`、`finance_manager` 等）。组里没人时任务不会报错，只会**停在无人认领状态**；而主待办此时已锁定（`canApprove=false`），业务上表现为「单据卡住，谁都批不了」。

**判定特征**：子流程实例存在、当前节点 `assignee` 为空、部门侧待办列表谁都看不到。

### R2 账号 / 口令与演示数据不一致 → 401 或登录即被顶下线

**机理**：
1. `DemoUserInitializer` 对**已存在用户直接 `continue`，不重置口令**。目标库若已有同名账号且密码 ≠ `demo`，初始化器不会修，表现为"密码没错但登不上"。
2. 系统启用单会话控制：同一账号二次登录会顶掉旧会话，旧会话后续请求返回
   `{"message":"该账号已在其它设备登录，当前会话已失效"}`。
3. 冒烟脚本用单一口令 `SMOKE_PASS`（默认 `demo`），真实组织一人一密时无法直接跑。

**判定特征**：登录接口 401；或已登录页面突然全量 401 且提示"已在其它设备登录"。

## 1. P0 检查项（必须全绿）

### A. 组织与岗位组配置（对应 R1）

- [ ] **A1** 目标环境中三个部门（通用适用全体 / `dept_legal` / `dept_finance`）的部门组（类型 `DEPARTMENT`）均已建立且成员非空
- [ ] **A2** 通用流程文书组 `<deptId>_clerk` 已按部门逐一配置，且**每个组至少 1 人**（不能依赖"回退到部门第一人"）
- [ ] **A3** 法务部四个岗位组均已配人：`dept_legal_clerk`、`legal_compliance`、`legal_business`、`legal_manager`
- [ ] **A4** 财务部四个岗位组均已配人：`dept_finance_clerk`、`finance_budget`、`finance_treasury`、`finance_manager`
- [ ] **A5** 每个岗位组至少 1 人（只有 1 人时确认为有意为之，该人休假即流程停摆）
- [ ] **A6** 部门负责人 / 发起人 `manager` 账号存在且可用（BPMN 中为 `camunda:assignee="manager"` 硬编码，不走组）
- [ ] **A7** 用真实账号清单替换掉所有演示账号：`alice` / `bob` / `grace` / `frank` / `henry` / `mallory` 不再作为唯一承接人

### B. 账号与口令（对应 R2）

- [ ] **B1** 目标库中同名演示账号的**实际口令**已核实（不要假设仍是 `demo`）
- [ ] **B2** 若与 `demo` 不一致，改脚本环境变量 `SMOKE_PASS` / `SMOKE_MANAGER_PASS`，或统一改密后再初始化
- [ ] **B3** 已确认单会话策略为**有意设计**，并告知用户"另一处登录会顶掉本处"
- [ ] **B4** 冒烟脚本执行人不与真实用户共用同一账号（否则互相顶下线，结果不可信）
- [ ] **B5** 若真实组织一人一密，已确认需按账号拆 `SMOKE_*_PASS`（脚本当前仅支持单一口令）

### C. 流程定义与注册表

- [ ] **C1** 三个 BPMN（`dept_comm_general` / `dept_comm_legal_contract` / `dept_comm_finance_budget`）在目标引擎中**已部署且为最新版本**
- [ ] **C2** `BIZ_SUBPROCESS_DEF_` 注册表中三条记录均为启用状态
- [ ] **C3** 数据库表 `dept_subprocess_registry` 已由 `V5__dept_subprocess_registry.sql` 建立（按目标方言执行）
- [ ] **C4** 目标方言的 V5 脚本已实际执行并校验表/索引/版本号（本项目**只实测过 H2**，MySQL / PostgreSQL / Oracle 等须单独验证）
- [ ] **C5** 跨部门启动已被拒绝（选错部门时接口报错、主待办**不锁定**）——建议手工复现一次
- [ ] **C6** 未传 `subProcessKey` 的旧调用方仍走 `dept_communication` 单节点流程（回归）

### D. 前端交付

- [ ] **D1** 已重新执行 `npm run build`，构建产物为最新
- [ ] **D2** 已**强制刷新**浏览器（Ctrl+F5 / 清缓存），确认 `TaskDrawer` 为最新 chunk——旧 chunk 里没有部门侧提交按钮
- [ ] **D3** 待办抽屉页脚可同时看到「发起沟通」「部门沟通」，且「部门沟通」同样受 `canInitiate` 约束

- [ ] **D5** 子流程结束后抽屉自动关闭并刷新列表

### E. 上线前真实冒烟（禁止在生产库执行）

- [ ] **E5** 冒烟数据已清理或明确标记为可丢弃（每条流程各写入一条申请 + 一条子流程实例）

## 2. P1 检查项（可带条件上线，须登记责任人）

| 编号 | 事项 | 风险 | 建议处理 |
|---|---|---|---|
| P1-1 | 非 H2 方言未验证（MySQL / PG / Oracle / DM / 人大金仓 / SQLServer…） | 迁移脚本或分页/时间类型可能不兼容 | 上线环境先用 V5 脚本在等价库演练一遍 |
| P1-2 | 前端旧 chunk 缓存 | 用户看不到新按钮 / 新提交入口 | 发布说明中明确要求强刷；必要时改 chunk hash 前缀 |
| P1-3 | 一人多岗（演示数据特征） | 真实组织中若一人挂多岗，待办列表上限 8/12 条可能漏 | 按实际待办量调整脚本遍历上限 |
| P1-4 | 文书组未配置时的回退逻辑（部门第一人） | 文书可能落到不合适的人身上 | 正式环境强制配置文书组，A2 项打勾 |
| P1-5 | 部门侧「重新分发 / 退回补充」仅通用流程支持 | 专属流程无退回，用户可能误操作 | 业务侧提前沟通口径 |
| P1-6 | 后端 81 个用例本轮未重新确认 | 若同期有其它改动，回归状态未知 | 上线前跑一次 `mvn -o test` |
| P1-7 | 真实浏览器人工点击覆盖有限（脚本为主） | 极端分辨率 / 特殊浏览器未验证 | 请业务方在 Chrome + 内网门户各点一次 |

## 5. 本清单的边界（如实说明）

1. 清单条目来自三份过程验收报告与汇总单的**结论与遗留风险**，40 步实测均在 **H2 + 演示账号**环境完成，**未在真实组织数据、真实浏览器多端、多数据库方言下复验**。
2. 清单中 A/B 两组是"配置核对"，无法靠自动化脚本替代——脚本跑得过只能证明演示数据自洽。
3. 「两条 P0 高风险」的分级口径为：**会导致业务单据永久卡死（R1）** 与 **会导致全员无法登录（R2）**，其余归 P1。
4. 本清单不覆盖 Camunda Run 架构迁移（`userlib` 加载、jackson 版本冲突等），那是另一条独立的上线路径。
