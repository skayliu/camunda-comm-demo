# 岗位组配人核对表（实施填写版）

> 用途：真实组织切换时，逐格填人并签字确认。演示库里这些组本来就配齐了，**本表只有换成真实组织时才真正起作用**。
>
> 适用工程：`camunda-comm-demo`　版本口径：V5 注册表 + 三条部门沟通子流程
> 生成方式：静态读取 `DemoUserInitializer`、三个 BPMN、`SubProcessDefService`、`DeptSubTaskService`、`CommunicationController` 与 V5 迁移脚本，**未连库执行**。

---

## 0. 先理解四条硬规则（填表前必读）

| # | 规则 | 代码依据 | 对填表的影响 |
|---|---|---|---|
| 1 | 文书解析只取**组内排序第一个**，不是"组内谁都行" | `SubProcessDefService.resolveClerk()`：`identityService.createUserQuery().memberOfGroup(clerkGroup).list()` 后取 `clerks.get(0)` | **文书组里填两个人不会产生备份效果**，第二个人永远收不到待办 |
| 2 | `<deptId>_clerk` 为空时回退**部门组第一个成员** | 同上，`resolveClerk` 第二段 `memberOfGroup(deptId)` 取 `members.get(0)` | 不配文书不会报错，会静默落到某个部门成员身上——这是隐性风险 |
| 3 | 专属流程节点用 `candidateGroups`，组内多人是**竞争认领** | 法务/财务 BPMN 的 `camunda:candidateGroups` | 多人不是重复受理，但**组为空 = 谁都看不见待办** |
| 4 | 通用流程的经办人**必须是该部门组成员**，与岗位组无关 | `DeptSubTaskService.dispatch()` → `isDeptMember(id, deptId)`，不满足直接抛"不属于本部门" | 只把人放进岗位组、没放进部门组，分发会被拒 |

另外两条容易漏的：

- 部门选择器只认 `type = DEPARTMENT` 的组（`CommunicationController.departments()` 按 `groupType("DEPARTMENT")` 过滤）。**新建部门组时组类型填错，前端下拉里根本不会出现**。
- 文书/成员解析失败时抛业务异常而不是卡住："部门 X 暂无成员，无法指定文书"——这是正确失败，但要提前配人。

**填写要点**

1. "实际生效人"填**组内账号排序最小的那个**。若组里有 `alice`、`zoe`，生效的是 `alice`，`zoe` 只是挂名。
2. 因为规则 1，**备份不能靠"多填一个人进组"实现**。真实备份只有两条路：
   - 发起后由管理员把文书节点**手工转派**给备份人（推荐，规则内可行）；
   - 临时把备份人调整为组内排序最小（需删改组关系，有操作风险）。
   请在"备份方案"列勾选，并在上线检查清单对应项签字。
3. 本组为空时**不报错**，会静默回退到部门组第一个成员。若该人不具备文书职能，需在上线前发现——判定方法是发起一条通用流程，看 `Task_ClerkDispatch` 的 assignee 是否等于预期人。

## 5. 填完之后：三步只读自检

### 5.1 列出所有相关组的成员数（一次性看空空组）

```sql
SELECT g.ID_ AS group_id, g.NAME_ AS group_name, g.TYPE_ AS group_type,
       COUNT(m.USER_ID_) AS member_count
FROM ACT_ID_GROUP g
LEFT JOIN ACT_ID_MEMBERSHIP m ON m.GROUP_ID_ = g.ID_
WHERE g.TYPE_ = 'DEPARTMENT'
   OR g.ID_ LIKE '%\_clerk' ESCAPE '\'
   OR g.ID_ IN ('legal_compliance','legal_business','legal_manager',
                'finance_budget','finance_treasury','finance_manager')
GROUP BY g.ID_, g.NAME_, g.TYPE_
ORDER BY member_count ASC;
```

`member_count = 0` 的行就是会卡住流程的组。

### 5.2 预演文书解析结果（与 `resolveClerk` 近似一致）

```sql
SELECT m.GROUP_ID_, m.USER_ID_
FROM ACT_ID_MEMBERSHIP m
WHERE m.GROUP_ID_ IN ('dept_it_clerk','dept_admin_clerk','dept_legal_clerk','dept_finance_clerk')
ORDER BY m.GROUP_ID_, m.USER_ID_;
```

每个组的第一行即实际生效人。**注意这是近似值**：`resolveClerk` 走 Camunda `UserQuery` 的默认排序，与数据库排序在大小写/多语言账号下可能不同，最终以"发起一条流程看 assignee"为准。

## 6. 三条 P0 判定特征（现场识别用）

| 现象 | 最可能原因 | 处置 |
|---|---|---|
| 子流程实例存在、当前节点 `assignee` 为空、部门侧谁都看不到待办、主待办 `canApprove=false` | 岗位组无人（表 C）或文书组无人且部门组也为空（表 B） | **补人后手工转派**，不要删实例 |
| 前端部门下拉里没有该部门 | 组类型不是 `DEPARTMENT`（表 A） | 改组类型，重启后刷新 |
| 分发提交提示"经办人 X 不属于本部门" | 人在岗位组但不在部门组（表 D） | 补部门组成员关系 |
